Rate limiting.

Two limiters. A global per-IP token bucket protects the gateway from any single address. Per-route sliding windows protect your services from any single user, key or IP. Both count in Redis, so every gateway pod sees the same numbers.

02:14, the first night

A partner's script sent 900 requests a second to orders, which had no limit. Three lines of YAML would have turned that into 429s at the door.

Before, in orders
import rateLimit from 'express-rate-limit';
// memory store: each pod counts on its own,
// so 4 pods = 4x the intended limit
app.post('/v1/orders', rateLimit({
  windowMs: 60_000, max: 30,
  keyGenerator: (req) => req.user,
}), createOrder);
After, in orders.yml
- path: /v1/orders
  methods: [POST]
  rateLimit: { perMinute: 30, key: USER }

Per route

rateLimit:
  perMinute: 120
  perDay: 5000
  key: USER_OR_IP     # IP | USER | API_KEY | USER_OR_IP | IP_USER
  group: search       # optional: share one quota across routes with the same group
  hideHeaders: false  # true: no X-RateLimit-* headers to the client
  blockFor: 900       # optional: after a rejection, block the caller on this route for 900 s
KeyCounts per
IPclient address, as resolved by TRUST_PROXY
USERthe user id from auth; falls back to IP when anonymous
API_KEYthe X-API-Key header; falls back to IP
USER_OR_IPuser when logged in, IP otherwise
IP_USERthe pair, so one user on two devices gets two quotas

Blocking repeat offenders

Add blockFor (seconds) to a route's limit and the first rejection blocks that caller on that route for that long, on every pod. Use it on login, OTP and password-reset routes: an attacker who hits the limit waits out the block instead of retrying the moment the window slides. Retries during the block do not extend it. The block is per route and per key, so other routes and other callers are untouched.

- path: /auth/otp/verify
  methods: [POST]
  bypass: [AUTH]
  rateLimit: { perMinute: 5, key: IP, blockFor: 900 }

Each gateway worker also remembers callers it has just rejected, for the global IP limiter as well as route limits, until their Retry-After runs out. Repeat requests from them are answered from memory, re-checked with Redis at most every 5 seconds, so a flood of rejected traffic barely touches Redis and deleting a block in Redis (blocked:ip:<ip> or a route's …:blocked key) frees the caller within 5 seconds. Rejected requests were never counted, so this changes no limit. The memory holds at most 10,000 callers per worker.

A route's day and minute limits are checked together in one atomic Redis call, and a request counts against both only if both allow it: a burst the minute limit turns away does not use up the day.

Each window is a sliding-window counter: one small Redis hash per key holding this window's count and the last window's, with the last one weighted by how much of it still overlaps. That is the approximation Cloudflare uses; it needs three fields per key however many requests a user makes, where a sorted-set log stores one entry per request. It runs as one Lua script per window, sent as EVALSHA. The day window runs first, so a daily rejection does not consume a minute token.

Headers the client sees

HeaderExample
X-RateLimit-Limit, -Remaining, -Reset120, 17, 42
RateLimit-Limit, -Remaining, -Reset120, 120;w=60 / 17 / 42
Retry-After on 42942

Both families, because clients written for Kong read one and clients written for Envoy read the other. Reset values are seconds until the window frees up. When two windows apply, the headers describe the tighter one.

The global IP bucket

Every request first passes a token bucket per client IP: IP_RATE_LIMIT_CAPACITY tokens (200), refilled at IP_RATE_LIMIT_REFILL_RATE a second (5). An address that gets 429 twenty times in a minute is blocked for fifteen minutes with a 403. Addresses in TRUSTED_IPS skip both limiters.

This limiter keys on the client IP. Behind a load balancer that IP comes from X-Forwarded-For, which Sancus only believes when TRUST_PROXY says the peer is a proxy. Get that wrong and every user shares one bucket. Sancus refuses to start with TRUST_PROXY=false while this limiter is on. Set IP_RATE_LIMIT_ENABLED=false if your balancer already does per-IP protection.

Order matters

A cache hit is answered before the rate limiter runs. A hit costs no upstream work, so it is not counted. Put limits on routes that are expensive, not on routes that are cached.

When Redis is down

Requests go through, with no rate-limit headers, and a warning in the log. A Redis outage should not take your API with it.
